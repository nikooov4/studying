## Результаты и ошибки

- Пользователь явно разрешил начать день 6 при незавершённых алгоритмах дней 3–5. Эти задачи остаются отдельным долгом; CSV не менялся.
- Recall `errors.As`: после уточнений верно объяснил, что `errors.As(err, &validationErr)` записывает в `validationErr` указатель на найденную ошибку типа `*ValidationError`. Потребовалось напомнить: `var validationErr *ValidationError` имеет значение `nil`; `&validationErr` — адрес переменной, а не объекта ошибки.
- Recall `defer`: верно предсказал вывод `1` для отложенного `fmt.Println(x)` перед последующим `x = 2`; уточнено, что аргументы вычисляются в момент выполнения `defer`.
- Recall deferred closure: верно предсказал вывод `2`; понимает, что переменная читается телом анонимной функции лишь при её отложенном вызове.
- Recall `errors.Is` / `errors.As`: верно выбрал `Is` для sentinel `ErrNotFound`, `As` для `*ValidationError`, когда нужно получить поля ошибки.
- Recall typed nil: верно предсказал `false` и назвал внутреннюю пару интерфейса `(*ValidationError, nil)`; понимает отличие от `(nil, nil)`.
- Packages/modules/visibility: верно построил import path `github.com/nik/shop/service` из module path и каталога пакета; уточнён синтаксис одной строки импорта в кавычках.
- Embedding: верно определил приоритет метода `Service.Log` и явный вызов embedded-метода `s.Logger.Log(...)`. Сначала назвал это перегрузкой; уточнено, что в Go её нет, а объявленный метод скрывает продвинутый.
- Basic layout: верно поместил бизнес-правило о непустом идентификаторе клиента в `service`; объяснил разделение обязанностей transport/service/repository. Уточнено: transport может валидировать форму HTTP-ввода, но бизнес-инвариант не должен зависеть от транспорта; для критичных инвариантов полезна также защита на уровне БД.
- Мини-практика: ученик создал отдельный module `niki`, корректные module-based imports и экспортируемую функцию transport; `go run ./cmd/app` успешно вывел `service -> repository`. Ещё исправить: transport импортирует и получает repository напрямую, хотя по условию должен зависеть только от service; `gofmt -d` показал неотформатированные файлы.
- Повторная проверка: граница исправлена — transport зависит только от service, service хранит repository, main собирает зависимости; вывод `service -> repository` подтверждён. `gofmt -d` всё ещё не пустой; после форматирования проверить ещё раз. В transport есть неиспользуемый тип `Transport` — не ошибка компиляции, но его следует либо задействовать, либо удалить как лишний.
- Финальная проверка: ученик удалил лишний неиспользуемый тип `Transport`; `gofmt -d` пустой; `go run ./cmd/app` подтверждён с выводом `service -> repository`.
- Self-check: верно назвал `main` composition root, который связывает зависимости. После уточнения объяснил преимущество: repository можно заменить, в том числе тестовой реализацией, без изменения service-слоя.
