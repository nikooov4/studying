## Точка продолжения

- Текущий этап: recall.
- Recall зачтён: ученик объяснил, что receive из пустого открытого buffered channel ждёт данные, а send в полный buffered channel — свободное место. Первичный ответ исправлен.
- Текущий этап: теория `close(channel)`.
- Теория `close(channel)`: ученик верно указал, что повторный `close` вызывает panic, а receive из пустого закрытого канала возвращает zero value и `ok == false`; верно обосновал, что закрытие принадлежит отправителю. Затем ошибочно перенёс форму `v, ok := <-ch` на send в уже закрытый канал. Повторить различие receive и send после `close`.
- Теория `close(channel)` зачтена: ученик исправил ответ — send в закрытый channel вызывает panic.
- Теория `range` зачтена: ученик объяснил, что цикл читает до закрытия; уточнено, что пустой открытый channel означает возможность будущих значений, поэтому receiver ждёт.
- Текущий этап: мини-практика, исправление после review.
- Проверка первой версии `practice/day-10/exercise-01/main.go`: `go run main.go` и `go vet main.go` завершились без диагностики, но вывод пустой, потому что `main` завершается, не дожидаясь единственной goroutine. `gofmt -d main.go` показал только нормализацию форматирования.
- Найдено: (1) `range n` при `n=1000` выдаёт 0..999, а нужны 1..N и N=5; (2) все три stages вызываются последовательно внутри одной goroutine, поэтому при ожидании `main` generator заблокируется на первом send в unbuffered channel, и square не начнётся; (3) consumer сначала полностью вычитывает `in`, а затем передаёт уже опустошённый закрытый channel в `sum`, поэтому сумма получится 0; (4) нет механизма ожидания завершения pipeline.
- Проверка второй версии: отдельные goroutines для generator/square/consumer добавлены; `go vet main.go` без замечаний. `go run main.go` напечатал только `332833500` — это сумма квадратов 1..999. Ошибки: (1) `generator(1000)` и условие `i < n` дают 1..999, не 1..5; (2) `defer fmt.Println(sum(in))` немедленно вычисляет аргумент `sum(in)` при регистрации defer, поэтому `sum` полностью читает channel ещё до следующего `range`, а consumer не печатает значения; (3) `time.Sleep` не доказывает завершение pipeline и зависит от скорости выполнения; (4) `gofmt -d` всё ещё показал diff.
- Проверка третьей версии: consumer теперь корректно печатает значения и считает сумму при единственном `range`, но `go run main.go` завершается с `panic: close of closed channel` в `consumer`. `square` уже закрыл `ch2` как владелец отправок, после чего consumer пытается закрыть тот же channel. `go vet` не обнаруживает такую runtime-ошибку. `time.Sleep` и diff `gofmt` остались.
- Проверка четвёртой версии: double close устранён; stages запускаются отдельно; `sync.WaitGroup` корректно удерживает `main` до завершения всех stages; `go run main.go` завершился без panic, `go vet main.go` без замечаний. Ownership корректен: generator закрывает `ch1`, square закрывает `ch2`, consumer только читает. Единственная функциональная ошибка — при `generator(5)` условие `i < n` отправляет только 1..4, поэтому вывод `1, 4, 9, 16` и сумма 30 вместо требуемых `1, 4, 9, 16, 25` и 55. `gofmt -d` показывает diff только из-за перевода строк.
- Финальная проверка: граница исправлена на включительную. `go run main.go` вывел `1, 4, 9, 16, 25, 55`; `go vet main.go` без замечаний. Мини-практика зачтена.
